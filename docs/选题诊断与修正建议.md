# 帕米尔冰湖选题：诊断与修正建议（第二轮）

> 核对时间：2026-10
> 目的：把"能不能做"和"能不能拿分"分开判断。前者是技术问题，后者是叙事问题，两者不要混在一起解决。

---

## 0. 结论先行

1. **选题成立，形态也选对了。** 本地性（塔什库尔干属喀什）、跨境流域（阿姆河源区）、数据全公开、技术路线成熟——这四条同时满足的选题不多。科技发明制作类要的是"做出来能用、能验证"，你现在的形态对得上。

2. **技术栈里有一处会直接让程序起不来，但它不是"PySide6 vs PyQGIS"的绑定冲突那么简单。** 现状是：QGIS 3.x 走 Qt5+PyQt5，QGIS 4.0（2026-03 发布）走 Qt6+**PyQt6**，**两条线都没有 PySide6 绑定**。所以问题不是"版本没对上"，而是"这条路本来就不通"。解法只有两个：换 PyQt6，或者不用 QGIS。我建议后者，理由见 §2。

3. **最该改的不是技术，是"风险分级"这个交付物。** 专家权重打分模型在答辩现场几乎必然被问穿。改成可审计的分层规则筛查 + 阈值敏感性分析，同样的工作量，防守强度差一个量级。见 §4。

4. **一个被漏掉的风险：塔什库尔干是边境县。** 测绘法与地理信息安全对边境地区成图有限制，展板地图、成果图件、坐标精度都要提前规划。这一条现在不处理，到省赛送审阶段会被动。见 §6。

## 1. 选题口径：删两个词，加一句话

### 要删的

- **"预警"** → 改"风险识别与早期识别（early identification）"。真正的 early warning 要求准实时监测 + 阈值触发 + 通信链路 + 下游响应，离线桌面系统撑不起。这个词一被追问就是失分点，而且是不必要的失分。
- **"现有研究多为单湖定性评估"** → 这句话站不住。GLOF 是成熟领域：Huggel 的多指标框架、ICIMOD 的 HKH 冰湖编目、Emmer 的 GLOF 数据库、区域尺度自动提取都已成体系。写成"研究空白"等于给评委递刀。

### 要加的一句话

申报书和答辩 PPT 上，评委只会记住一句话。建议这句：

> **在帕米尔高原多云多雪条件下，把光学与雷达合成一条可复现的冰湖自动提取流水线，并输出下游中巴公路（G314）沿线的暴露度清单。**

场景、难点、产出三样齐了。而且每个词都能落到你实际做的东西上——这就是"能答得上"的标准。

创新点定位到**工程集成**，不是科学首创：

- 光学 + SAR 在高原多云条件下的自动化融合流程（可复现、有代码、有精度表）
- 冰雪/阴影误判的规则化剔除（不是新算法，是可靠的工程处理链）
- 暴露度评估落到具体路段与居民点（有清单、有数字）
- 桌面平台 + 开源工具链，别人能拿去复现

## 2. 技术栈：现状已经变了，结论要跟着变

### 2.1 绑定这件事的真实情况

| QGIS 线 | Qt 版本 | Python 绑定 | 能否与 PySide6 同进程 |
|---|---|---|---|
| 3.x 长期线（conda-forge 默认，最稳） | Qt5 | PyQt5 (sip) | **不能**，进程内会同时加载 Qt5 与 Qt6 两套库，符号冲突，直接崩 |
| 4.0（2026-03 发布） | Qt6 | **PyQt6** (sip) | 技术上同为 Qt6，但 shiboken 与 sip 两套包装层类型不互通，`QgsMapCanvas` 塞进 PySide6 的 layout 会出问题 |
| 任何线 | — | PySide6 | **不存在** |

也就是说：**"PySide6 主窗口 + PyQGIS" 这条路在两条线上都不通**，而且不是调参能解决的。

好消息是：**PyQt6 与 PySide6 的 API 差异极小**——主要是 import 名（`PyQt6.QtWidgets` vs `PySide6.QtWidgets`）、信号声明写法（`pyqtSignal` vs `Signal`）、以及部分枚举要写全限定名。你现有 Qt 能力迁移过去大约 1 天，不是"重写"。

所以决策变成：

- **路线 A**：PyQt6 + PyQGIS（地图零开发，运行时 1.5–2 GB）
- **路线 B**：PySide6 + rasterio + QGraphicsView 自绘（地图约 250 行，运行时 100–200 MB）
- **路线 C**：PySide6 + QWebEngineView + Leaflet（答辩兜底用，不做处理）

### 2.2 我建议走 B，但理由不是体积

上一轮把"打包 2 GB"当成主要理由，我认为这个理由被高估了——**答辩是你带自己的笔记本**，2 GB 环境在本机跑毫无问题，conda-pack 也只是传输问题。真正该权衡的是另外三件事：

1. **卡住时无人可问。** 六个月的学生项目，最贵的成本不是开发量，是"踩坑后能不能在一天内爬出来"。PyQGIS 独立应用（非插件）要手动设 `QGIS_PREFIX_PATH`、`PROJ_LIB`、`GDAL_DATA`，provider 才找得到数据；GDAL 双份（conda 装 qgis 后 pip 装 rasterio）会让 PROJ 数据库打架。这些坑中文资料少、报错信息晦涩。而 rasterio + PySide6 的报错你能直接搜到答案。
2. **答辩环境的确定性。** 评委面前程序起不来，前面的分数全丢。依赖越少，现场风险越低。这一条对科技发明制作类的权重比"功能多"高。
3. **你的地图需求其实只有四件事**：显示 GeoTIFF、叠多边形、缩放平移、点选查属性。为这四件事背一整套 GIS 引擎，投入产出不划算。

**什么情况下反过来选 A**：如果指导老师或实验室已有 QGIS 积累、身边有人能帮你 debug 环境——那 A 明显更省，因为地图部分确实近乎零开发。这时候**主窗口必须写 PyQt6，全程不要出现 PySide6**。

### 2.3 走 B 的话，具体怎么写（约 250 行的量级）

> **2026-10-26 决策变更：界面层改用 QML（Qt Quick），本节的 QGraphicsView 自绘方案作废。**
> 不变的东西：分层硬约束（core 不碰 Qt）、只调 core 公开接口的纪律、
> spike 已验证的"整景解码、渲染完丢栈"原则（§8.2）。
> 技术映射：QGraphicsView 画布 → Flickable + Image（QQuickImageProvider 提供栅格）；
> 风险多边形叠加 → QtQuick.Shapes（化妆笔 strokeWidth = 1/zoom）；
> 时序曲线 → QtCharts ChartView；风险表 → TableView + QAbstractTableModel；
> 后台任务不变（QThread + 信号回主线程）。
> 新增的两个已知风险点：QtCharts 在 offscreen+software 后端下的可用性（冒烟先行验证）、
> QML 与 Python 上下文属性名的一致性（靠接口契约 + 集成联调把关）。
> 界面冒烟统一跑 offscreen + software 后端，真机 GPU 路径由桌面运行覆盖。

原 QGraphicsView 方案（留档，供回退参考）：

```
rasterio 读窗口（按当前视图算窗口，带 overview 降采样）
  → numpy 拉伸（2%–98% 百分位，或固定 DN 区间）
  → QImage（注意 stride 与 BGR 顺序）
  → QGraphicsPixmapItem 放到 QGraphicsView
缩放平移：QGraphicsView 自带；滚轮事件里改 transform 后重新读窗口（分级重采样，别整景读）
多边形：QGraphicsPolygonItem + QPen/QBrush 按等级取色
坐标：pyproj 做 WGS84 ↔ CGCS2000 / UTM 43N 转换
点选：QGraphicsScene.itemAt 拿图元，反查属性表
```

关键性能点只有一个：**永远不要一次性把整景读进内存**，按视图窗口 + overview 分级读取，否则 10 m 的 Sentinel-2 一放大就卡死。

**架构上必须解耦**：算法层是纯 Python 包（`glof/core/`），不 import 任何 Qt；界面层只调 `glof/core` 的接口。这样第 3 月你就能在没有界面的情况下跑批量、出精度表，界面拖延也不会拖死主线。

### 2.4 推荐技术栈清单（照这个装，别加别的）

既然不用 QGIS，**就不需要 conda 了**。整条链 pip 装完，GDAL 只存在一份（rasterio / pyproj / pyogrio 的 wheel 各自静态打包 GDAL+PROJ），PyInstaller 也干净得多。这是放弃 PyQGIS 带来的最大附带好处，别浪费掉。

| 层 | 选型 | 说明 |
|---|---|---|
| 运行时 | Python 3.11 / 3.12 | wheel 覆盖最全。若只有 3.13，先 `pip install rasterio` 看有没有 cp313 轮子，没有再降版本 |
| 界面 | **PySide6** | Qt6，LGPL，不传染。与 PyQt6 二选一，既然不用 QGIS 就用你最熟的 |
| 地图画布 | **QGraphicsView + QGraphicsPixmapItem** | 自绘，约 250 行，见 2.3 |
| 影像读写 | **rasterio** | 窗口读取 + `overviews` 分级降采样 |
| 坐标转换 | **pyproj** | WGS84 ↔ CGCS2000 ↔ UTM 43N |
| 数组 / 形态学 | **numpy + scikit-image** | `label` / `regionprops` / 闭运算 |
| 矢量化 | **rasterio.features.shapes + pyogrio** | 输出 GeoJSON / GPKG |
| 时序 | **pandas** | |
| 曲线 | **pyqtgraph**（屏上）+ **matplotlib**（导出报告图） | pyqtgraph 交互顺，matplotlib 出图正式，两个都用 |
| 数据获取 | **pystac-client** + `planetary-computer` / Copernicus Data Space | 检索 → 读窗口，不整景下载 |
| SAR | **hyp3_sdk**（ASF HyP3） | RTC 产品，自带 layover-shadow mask |
| 报告 | **python-docx + jinja2**（或 docxtpl） | 模板化，别手搓 docx |
| 打包 | **PyInstaller `--onedir`** | 100–200 MB。不要 `--onefile`，启动会慢到被评委等 |

**明确不装**：QGIS / PyQGIS、Google Earth Engine、SNAP、pyroSAR、conda（既然不用 QGIS）。少一个依赖少一个坑。

**唯一的硬约束**：GDAL 只能有一份。所以**要么全 pip wheel、要么全 conda，绝对不要混**。全 pip 是本方案的默认选择。

**答辩兜底版**（半天工作量）：PySide6 + `QWebEngineView` + Leaflet/MapLibre，读预先导出的 PNG 瓦片和 GeoJSON，只做展示不做处理。用途只有一个——万一现场主程序起不来，你有东西可以放。

## 3. 算法：三处需要修正

### 3.1 MNDWI 对冰雪"更稳"这个说法要反过来

这是上一轮的一个实质性错误，必须纠正：

- 雪/冰在 **SWIR 波段反射率很低**，而 MNDWI = (Green − SWIR1)/(Green + SWIR1)，雪会算出**高值** → 把雪判成水。
- 冰湖制图的主流路线（ICIMOD / HKH 编目）用的是 **NDWI + NDSI 掩膜**，不是 MNDWI 打主力。

正确的处理顺序：

```
云/云影掩膜（S2 自带 QA 波段，或 s2cloudless）
  → NDSI > 0.4 且 NIR > 0.11 掩掉冰雪
  → NDWI（或 AWEIsh）提水
  → 地形阴影/叠掩掩膜（SAR 侧见 3.2）
  → 最小面积过滤（skimage.measure.label + regionprops，按投影面积算）
  → 形态学闭运算补洞
  → 矢量化（rasterio.features.shapes → GeoJSON/GPKG）
```

MNDWI **留着做消融对比**，不要当主力，也不要在方案里预设"MNDWI 更稳"这个结论——万一你自己跑出来的数据不支持，就白写了一句。

> **代码跑通后补的一条实测修正（2026-10-26）**
>
> 上面这段说对了一半。把公式并排看会发现：MNDWI = (Green − SWIR1)/(Green + SWIR1)，
> NDSI = (Green − SWIR1)/(Green + SWIR1)，**两者是同一个公式**，逐像元数值完全相等。
> 所以真正的坑不是"选哪个指数"，而是**冰雪掩膜必须加 NIR 门控**。
>
> 合成影像上的六组对照（见 `README.md`）：
>
> - 只按 NDSI>0.4 掩膜：水的 NDSI 中位数 0.746，**湖被自己的掩膜删光，0 个水体**
> - 掩膜加上 NIR>0.11 后：MNDWI 也能得到正确结果（0.3036 km²，与 NDWI 完全一致）
> - `--threshold otsu` 在多雪场景切到 −0.4458，即 land/snow 分界，把整片雪判成水
>
> 结论修正为：**NDWI 仍是首选**（HKH 编目标准、对浑浊水体的 SWIR 噪声更钝），
> 但"掩膜带 NIR"这一条比"选哪个指数"更关键。这两句话都要写进申报书——
> 答辩时能当场拿出对照数据，比引一篇文献有力得多。

### 3.2 SAR 侧：直接用 RTC 产品自带的阴影掩膜

这一点能省你不少事，而且官方文档写明了：**ASF HyP3 的 RTC 产品包里自带 Layover-Shadow mask 栅格**。也就是说"地形阴影剔除"这个关键问题（你列的第二个关键问题）不需要自己用 DEM 算 hillshade 再阈值——直接读产品里的掩膜。

配套要点：

- 默认 **gamma0**（对地形更稳），像元间距 10/20/30 m 可选，DEM 用 Copernicus GLO-30（30 m）。**建议先用 30 m**，文件小一个量级，跑通了再上 10 m。
- **HyP3 现在是 credit 制**，免费额度约 8000 credits/月。先按"研究区 × 时相数"算清楚要多少景，一次性规划好批量下单，不要边试边跑把额度烧光。
- 高原水体用 **VV 绝对阈值不稳**：风浪、浮冰、强风都会抬高后向散射。建议 VV + VH 双极化，或用**双时相变化检测**（溃决前后 / 消融季首末）代替绝对阈值——后者对阈值不敏感，也更符合"变化识别"的叙事。

### 3.3 时序：只做消融期，不做 12 个月

帕米尔 10 月—次年 4 月湖面结冰，NDWI 直接失效，而且云量大。只做 **6–9 月**，年际序列 2015–2026，Landsat 8/9 补 30 m 密度。这个取舍要**明确写进方案**——评委看到你主动排除无效时相，是加分的（说明你想过）。

## 4. 风险分级：别用专家权重打分

这是整个项目**最容易被问穿**的地方，也是上一轮点到但没给替代方案的地方。

### 问题

加权求和模型（面积 × w1 + 扩张速率 × w2 + 坝体类型 × w3 + …）在答辩现场会被问：**"这些权重怎么来的？"** 你只能答"参考文献"或"专家经验"，然后被追问"换个权重排序会变吗"——一旦承认会变，整个模型就废了。

### 替代方案：分层规则筛查 + 敏感性分析

不做综合指数，做**可审计的分级规则**：

```
一级（候选）：面积 ≥ 0.02 km²  且  2015–2026 面积年增速 > 阈值
二级（潜在危险）：母冰川接触（冰面/冰前湖）  或  坝体为冰碛/冰坝
三级（有暴露）：下游 30 km 缓冲区内的 G314 里程 / 居民点 / 口岸
→ 输出：高（三级全中）/ 中（中两级）/ 低（仅一级）
→ 每条判据附命中情况，评委可自行复核
```

再配一个**阈值敏感性分析**：把面积阈值、增速阈值、缓冲区半径各扰动 ±20%，统计等级翻转比例。这一步成本极低（就是循环跑几遍），但答辩时是硬通货——你能直接说"阈值在 ±20% 内扰动，高等级湖的集合稳定度 87%"。

### 验证怎么做（样本少的现实解法）

塔什库尔干境内符合 0.01 km² 的冰湖可能只有几十个，历史溃决记录更少甚至没有。所以：

- **提取精度**：人工目视解译 100–200 个湖做验证集，算 IoU / F1 / 召回率，**分光学、SAR、融合三组**——这组数字就是你"融合不是噱头"的证据。
- **风险模型**：用区域已溃决冰湖回测（帕米尔/中亚/喜马拉雅公开事件），算命中率；再抽未溃决的高风险湖做对照。样本量必须如实写出来，**并明确说明这是定性验证不是统计验证**。主动承认限制，比被问出来强得多。
- **别做机器学习。** 正样本不够，做了也是过拟合，而且解释不了。

## 5. 研究区：不要简单"扩区"，要做分层

上一轮建议"扩到中国境内帕米尔或喀喇昆仑—帕米尔"，方向对，但会带来一个新矛盾：**挑战杯科技发明制作类的评分里"完成度"权重很高，扩区会稀释完成度**。

折中方案（建议照这个写进申报书）：

| 层次 | 范围 | 用途 |
|---|---|---|
| 算法验证层 | 塔什库尔干（本地） | 保"本地性"叙事，出精度表、出图 |
| 模型标定层 | 喀喇昆仑—帕米尔 / 全 HKH 公开 GLOF 事件库 | 凑正样本，做回测 |
| 展示层 | 塔什库尔干 + 下游 G314 走廊 | 暴露度清单、报告导出 |

即：**流程在本地跑通，模型用区域事件标定，成果落回本地**。这样"本地性"和"样本量"不再互斥。

**第 1 月就要做一次历史 GLOF 事件盘点**，用盘点结果决定研究区边界，别拖到第 5 月——那时候改研究区等于重跑全流程。

## 6. 一个容易漏的合规问题：边境县

塔什库尔干与塔吉克斯坦、阿富汗、巴基斯坦接壤，属边境地区。测绘法与地理信息安全对边境地区成图、高精度地理数据有明确管理要求。对学生项目，实操上注意四条就够：

1. **只用公开卫星影像**（Sentinel 10 m、Landsat 30 m 完全没问题），**不要自己飞无人机进边境区域**——这条也顺带解决了"第 6 月研究区实测"的可行性问题。
2. **成果图件用标准底图**：天地图 / 自然资源部标准地图服务，标注审图号。别自己画国界线、别用境外底图服务（Leaflet 默认底图要换成境内合规源）。
3. **不公开亚米级影像、精确坝体坐标、高精度 DEM 成果**。论文和展板给到 10 m 级、给到示意位置就够，不影响论证。
4. 如果走创业赛道要商业化，数据合规要单独评估——这也是选 B 路线（不依赖 QGIS 的 GPL）的一个附带好处。

**关于 GPL**：上一轮说"GPL 会传染，方案 B 没这个顾虑"——这个说法对学业赛道**被夸大了**。挑战杯学业赛道不涉及商业分发，用 GPL 库完全没问题；软著登记的是你自己的源代码，把 GPL 库当依赖不影响登记。只有走创业赛道、要做闭源商业产品时，GPL 才是真问题。别为了一个不存在的风险改技术路线。

### 7.1 先做数据接入，还是先搭平台：先数据

结论：**先数据，而且要设一个硬性 stop line。** 三条理由，第一条是决定性的。

**1. 数据会改接口，界面会按假数据的形状长歪。**

`glof/core/io.py` 原先的 `load_scene()` 只有一个全局等比缩放参数，隐含假设"所有波段同分辨率"。
真实 Sentinel-2 L2A 不满足这个假设（**已于 2026-10-26 改造完成，见本节末**）：

| 波段 | 原生分辨率 |
|---|---|
| B02 / B03 / B04 / B08 | 10 m |
| **B11 / B12** | **20 m** |
| B01 / B09 / B10 | 60 m |

也就是说，接真实数据的第一件事就是把 `io.py` 改成"逐波段重采样到统一参考网格"。
**这个改动一定会发生，只是早晚。** 如果界面先做，你会拿合成影像（6 个波段全 10 m）
把界面写死；等接上真实数据，缺 B11、网格不对齐、无数据边缘、一景跨两个 UTM 带，
界面就得返工。界面是被数据形状决定的，所以数据必须先定形状。

B11 的两种处理，选一个写进方案，别中途改：

- **（v1 推荐）读的时候直接重采样到 10 m 参考网格**，`rasterio.read(..., out_shape=...)`
  一条参数解决，代码最简单。代价是 SWIR 有插值痕迹，但 NDSI 只用来做雪/水判别的大块掩膜，
  这点误差不影响结果。
- **（更严谨）在 20 m 上算 NDSI 并阈值，再把得到的掩膜最近邻上采样到 10 m**。
  不污染 SWIR 光谱，但要多写一套网格对齐逻辑，且掩膜边缘会有块状台阶。

> **改造已完成（2026-10-26），按 v1 实现。**
>
> `load_scene()` 现在以最细分辨率的波段为参考网格，其余波段在 `read()` 时用 `out_shape`
> 一次重采样过去；同时支持多文件输入（每个波段一个文件、分辨率可不同），
> 也支持 `ref_resolution=20` 统一到 20 m 分析。
>
> 实测结果（`scripts/verify_resampling.py`，14 条断言全通过）：把 SWIR 拆成独立 20 m 文件后，
> NDWI 与单文件完全一致，NDSI 中位差异 0.0049、95 分位 0.0146，**湖泊面积差异 0.000%**。
> 也就是说 B11 重采样到 10 m 这一步没有引入可观测误差，v1 的取舍成立。
>
> 顺带修掉一个隐蔽错误：多波段文件只给路径时会默认读第 1 波段，
> 表现为"NDWI 全是噪声"而代码不报错。现在会抛 `RuntimeWarning` 并提示改成 `(路径, 波段号)`。

**2. 平台是确定性工作，数据是不确定性工作。**

界面写多少行你心里有数，随时能补。数据接入的坑是开放式的：账号与令牌、STAC 检索、
云量筛选、波段缺失、坐标系、网格对齐、无数据边缘、单景覆盖不全——任何一条都可能卡两周。
六个月项目里，**先消灭不确定性，再投入确定性工作**，这是排期风险管理的标准做法。

**3. 评分现实。** 科技发明制作类看"做出来能用、能验证"。一个能跑真实影像的
CLI 加一张精度表，分数高于一个漂亮的空壳界面。

#### 但界面不能无限推迟：必须提前做一次技术验证

有一件事不能等到第 5 月——**自绘地图的性能**。如果 `QGraphicsView` 拖不动
3000×3000 的真实影像，整个技术路线要重新评估，那时候改就来不及了。

所以：**第 3 月之前，花 2–3 天做一个 spike**——只做"能缩放平移 + 分级重采样读窗口"
这一个功能，丢一张真实大小的影像进去，看卡不卡。跑通就收起来继续做算法，跑不通立刻换方案。
这是唯一必须提前验证的技术风险，其余界面功能都可以往后放。

#### 数据接入的 stop line 与顺序

**stop line：两周内用一景真实影像跑通 `extract`，并出一张和目视解译对照的精度表。**
到点没跑通，就说明数据链有问题，必须先解决，不能带着问题去做界面。

1. **先不联网**：定下 B11 的处理方式（见上），把 `io.py` 改成逐波段重采样。
   用合成影像跑一遍，确保没改坏（`verify_pipeline.py` 九条断言仍然全绿）。
2. **再联网**：Copernicus Data Space Ecosystem 注册（国内可访问），拿到账号。
3. **检索 + 读窗口**：`pystac-client` 查一景塔什库尔干的 S2 L2A，`rasterio` 按窗口读，
   **不下载整景**。这一步跑通，第 1 月的核心风险就消掉了。
4. **跑真实阈值**：看 NDWI 在真实影像上的分布，定阈值，和目视解译的湖对比，出精度表。

做完这四步，再开始搭界面骨架。

> 团队两个人的话，第 1 步和 spike 可以并行（一个人改 io.py，一个人验证 QGraphicsView）。
> 一个人的话严格串行，别两头开工。

### 7.2 数据量预算：本地留 50 GB 就够

先把一件事说清楚：**这个项目不需要"下载一个数据集"，只需要按窗口读 + 裁剪后丢弃。**
Sentinel-2 一景 L2A 是 100 km × 100 km，12 年整景存下来 50 GB 以上，没人这么干。

按 6 波段（B02/B03/B04/B08/B11/B12，uint16）计算，压缩率按 0.5 估：

| 研究区范围 | 像元/波段 | 6 波段原始 | 压缩后/期 | 12 年（8 期/年） |
|---|---|---|---|---|
| 10 × 10 km | 1.0 M | 11 MB | 6 MB | 0.5 GB |
| 20 × 20 km | 4.0 M | 46 MB | 23 MB | 2.1 GB |
| **50 × 50 km** | **25 M** | **286 MB** | **143 MB** | **13.4 GB** |
| 100 × 100 km（整景） | 100 M | 1.1 GB | 572 MB | 53.6 GB |

**分项预算（按 50 km 研究区）：**

| 项 | 本地占用 | 说明 |
|---|---|---|
| S2 光学时序（12 年） | ~13 GB | 裁剪后保留，原始整景不落地 |
| SAR RTC（30 m，VV+VH，20 期） | ~0.4 GB | 裁剪后仅 21 MB/期；但**下载量** 534 MB/期，20 期约 10.7 GB 带宽 |
| DEM（Copernicus GLO-30） | ~11 MB | 可忽略 |
| 中间产品（掩膜、矢量、报告） | < 1 GB | |
| `.venv` | 400 MB | 已实测 |
| **合计** | **约 15 GB** | 留 50 GB 空间很宽松 |

**三条省钱建议：**

1. **先做 2018–2026，别一上来铺 12 年。** 2015–2016 只有 S2A 单星（10 天重访），
   2022–2024 期间 S2B 失效，也只剩单星。只有 2017–2021 是双星 5 天重访。
   时序密度本来就不均匀——这一点必须写进方案，否则"面积年际变化"会被采样差异污染。
2. **带宽是瓶颈，不是硬盘。** SAR 整景 RTC 534 MB/期，下载 20 期是 10.7 GB 流量，
   而裁剪后只留 0.4 GB。所以脚本要写成"下载 → 裁剪 → 删原始"，别先攒着再说。
3. **用 COG 远程读窗口**（Planetary Computer / Copernicus Data Space），
   本地只落裁剪结果。这一条能把 13 GB 的下载量压到 2–3 GB。

### 7.4 真实数据首次跑通（2026-10-26 实测）

**链路已端到端打通**：Planetary Computer STAC 检索 → SAS 签名 → rasterio 远程窗口读
→ 逐波段重采样 → NDWI/NDSI → 掩膜 → 矢量化 → 面积。全程不需要注册账号。

一个 20 km × 22 km 的 AOI、六波段 10 m，实测数据：

| 步骤 | 耗时 |
|---|---|
| STAC 检索（含云量过滤） | 1.7 s |
| SAS 签名 | 1.5 s |
| 六波段窗口读取 + 重采样 | 20.7 s |
| 落成本地 GeoTIFF（1765×2229，uint16 LZW） | 47 MB |

**但阈值不能直接用合成数据那一套。** 同一景、不同阈值：

| NDWI 阈值 | 水体数 | 总面积 km² | 中位 NDWI |
|---|---|---|---|
| **0.00** | **40** | **2.11** | 0.022 |
| 0.10 | 2 | 0.229 | 0.242 |
| **0.15** | **2** | **0.219** | 0.247 |
| 0.20 | 2 | 0.198 | 0.253 |
| 0.25 | 1 | 0.126 | 0.301 |
| 0.30 | 1 | 0.085 | 0.310 |
| 0.35 | 0 | — | — |

阈值 0 在真实数据上是灾难：40 个"水体"、中位 NDWI 只有 0.022，全贴着阈值，
看图全是雪斑边缘和河谷湿地的散点。**0.10–0.20 之间有一个稳定平台**
（2 个水体、面积 0.229 → 0.198 km²），说明 **0.15 是可信工作点**，0 不是。

**另一个更重要的结论：AOI 不能凭经纬度框选。**
实测两个框：

- 塔什库尔干河谷（75.15–75.35E, 37.65–37.85N）：提取出的"湖"沿河道分布，
  最大一个 6.07 km²、周长 108 km——那是河，不是湖。
- 冰川区（75.42–75.62E, 38.05–38.25N）：阈值 0 下 40 个散点，阈值 0.15 后几乎清空，
  说明该框内**本来就没有像样的冰湖**。

所以第 1 月的"历史 GLOF 事件盘点 + ICIMOD 编目核对"不是可选项，是**前置条件**：
研究框必须由已知冰湖的位置决定，不能凭感觉画。这件事没做之前，
阈值调得再准也是在错误的框里调。

**实测中修掉的三个 bug**（都会静默出错，值得记下来）：

1. `Path()` 会把 `https://...` 改写成 `https:\...`，GDAL 报 `Bad hostname`。
   远程 URL 一律保持字符串，只有本地路径才转 Path。
2. `BandSpec` 原本没有 `blue` 字段，导致 6 波段预设（blue=1..swir2=6）与实际落盘
   的 5 波段文件错位，读第 6 波段直接报错。
3. STAC 分页没设上限，`limit=10` 实际取了 101 景、耗时 23 s。分页必须以 `limit` 为总上限。

### 7.5 研究框定位：4 个测试湖，以及一个会推翻阈值设定的发现

**为什么要先定研究框**：阈值、精度、召回率只有落在**确定的测试湖**上才有意义。
在随机框出来的山上调阈值，调出来的数字既不能验证也不能写进报告。

#### 数据源现实

| 数据 | 状态 |
|---|---|
| ICIMOD「GLOF database of High Mountain Asia」（766 次事件，1533–2025，2025-12 更新，CC BY 4.0） | **需人工点一次下载**。页面是 JS 渲染，附件里只挂了 `glof.jpg`，自动化抓不到。地址：https://rds.icimod.org/metadata/8881454b-6f7c-461b-95c2-eaf7618230d9 （DOI: 10.26066/RDS.1973283） |
| OSM 水体 | **可自动获取**，用 Overpass API。作为独立第三方参考，避免循环论证 |
| Copernicus DEM（PC） | SAS 令牌对该存储账户返回 403，暂不可用 |
| OpenTopoData 高程接口 | 本机 SSL 握手超时，不可达 |

所以本轮的候选来自 OSM，脚本在 `scripts/candidate_sites.py`：
Overpass 取水体 → 算面积与紧凑度 → 逐个小窗口抓 S2 → **在 OSM 多边形内部**统计检出率。

> 指标必须算在多边形内部。大湖质心附近全是水，任何小窗口都会得到"100% 检出"，
> 这个数字毫无信息量。真正的指标是"OSM 多边形里有多少像元被判成水"。

#### 实测：中国境内帕米尔只有 4 个紧凑水体 ≥0.02 km²

| 湖 | OSM 面积 | 紧凑度 | 多边形内 NDWI | 检出 | **召回** |
|---|---|---|---|---|---|
| 喀拉库勒湖 | 5.041 km² | 0.36 | +0.146 | 3.191 km² | **63.3%** |
| 沙特瓦拉德库勒 | 1.476 km² | 0.40 | +0.040 | 0.234 km² | **15.9%** |
| （未名，75.375E/38.136N） | 0.573 km² | 0.63 | +0.194 | 0.500 km² | **87.1%** |
| 巴色克库勒 | 0.471 km² | 0.39 | +0.033 | 0.001 km² | **0.1%** |

**4 个已知湖里 2 个几乎完全漏检。** 当前算法（NDWI>0.15 + 冰雪掩膜）的基线召回率约 42%（面积加权）。

#### 为什么漏检：这些湖的 NDWI 只有 0.03–0.19

四个湖的多边形内部光谱中位数：

| 湖 | Green | Red | NIR | SWIR1 | NDWI |
|---|---|---|---|---|---|
| 喀拉库勒湖 | 0.158 | 0.126 | 0.112 | 0.110 | +0.171 |
| 沙特瓦拉德库勒 | 0.154 | 0.130 | 0.124 | 0.129 | +0.100 |
| 未名 | 0.176 | 0.124 | 0.109 | 0.116 | +0.234 |
| 巴色克库勒 | 0.147 | 0.130 | 0.127 | 0.133 | +0.063 |

**NIR 高达 0.11–0.13，而清澈水体的 NIR 应当 <0.03。** 这是典型的**高浊度冰川湖**
（岩粉悬浮物把可见光和近红外一起抬起来），也就是帕米尔冰湖的常态。
文献里 NDWI 0.3–0.6 的判水阈值，是给清澈水体定的，直接搬过来会系统性漏掉一半以上的真实湖。

**这条结论会推翻之前的阈值设定**：§7.4 在随机山框里标定出的 0.15，
在这个框里漏掉了 2/4 的已知湖。固定阈值这条路本身就有问题。

#### 下一步该做的三件事（按优先级）

1. **换成本地自适应阈值**：在 1–3 km 的滑动窗口内做 Otsu 或分位数分割，
   而不是全图一个常数。这是唯一能同时抓住清澈湖和浑浊湖的做法。
2. **人工下载 ICIMOD 的 GLOF 数据库**（一次点击），把 766 个事件里落在研究区的点
   叠上来，测试湖从 4 个扩到可用规模。**OSM 的 4 个是下限，不是真实数量。**
3. **样本量问题现在有了实测证据**：中国境内帕米尔在该 bbox 内只有 4 个紧凑水体 ≥0.02 km²。
   这印证了 §5 的判断——研究区必须扩到喀喇昆仑—帕米尔，否则风险分级做不起来。

#### 选题口径建议这样改

> **塔什库尔干县冰湖识别与溃决风险筛查——西帕米尔潜在风险区与东喀喇昆仑历史溃决区的双区对照**

三层结构，每一层都有明确作用：

1. **历史溃决区（克勒青河）**：4 个冰坝湖、38 次事件 → 正样本，用来验证召回率与面积时序
2. **潜在风险区（西帕米尔）**：4 个湖、零溃决记录 → 天然对照组，用来验证"不误报"
3. **暴露度**：叶尔羌河下游（阿尔塔什水利枢纽 + 喀什/和田绿洲灌区），
   比 G314 更有分量。2018-08-10 克亚吉尔溃决 3500 万 m³（约 3 个西湖），
   洪峰直达阿尔塔什枢纽围堰——有具体灾情可引用。

#### 一个必须在方案里写清楚的方法问题

克亚吉尔的溃决机制是**冰坝周期性溃决**（冰川前进阻塞河谷，湖充水后顶溃），
与冰碛坝溃决（溃口下切、管涌）完全不同。**用同一套风险判据覆盖两者在方法上站不住。**

正确处理是**分坝型、分判据**：

| 坝型 | 判据 |
|---|---|
| 冰坝湖 | 母冰川是否在前进 / 阻塞河谷；湖面面积是否接近历史溃决前的峰值 |
| 冰碛坝湖 | 母冰川接触关系；坝体下游坡度；面积扩张速率 |

这反而是个可以写进创新点的东西——**同一行政区内两类坝体的判据分离**，
比"全区域统一打分"扎实得多，也正好回应了 §4 里"专家权重无法辩护"的问题。

### 7.8 判水规则实测：滑窗 Otsu 不可用，光谱双条件最优

在 5 个已知湖上（OSM 的 4 个 + 克亚吉尔）对比三种规则，
同时记录**场景总水体**和**参考区外水体**——后者用来判断召回是不是靠"到处判成水"刷出来的。

| 规则 | 平均召回 | ≥50% 的湖 | 场景总水体 | 参考区外 |
|---|---|---|---|---|
| A. NDWI > 0.15 | 39.8% | 2/5 | 1.16 km² | 0.96 km² |
| **B. 滑窗 Otsu** | 74.7% | 4/5 | **9.27 km²** | **8.81 km²** |
| **C. NDWI > 0.02 且 NIR < 0.20** | **61.8%** | **4/5** | **1.97 km²** | 1.66 km² |

**滑窗 Otsu 的召回是假的。** 它在 5.5 km × 5.5 km 的窗口里判出 9.27 km² 水体
（占 31%），其中 8.81 km² 在参考湖之外——高原山地不可能有 31% 是水。
原因是 Otsu 假设直方图双峰，而窗口里水体只占 1% 时，
双峰落在"裸岩 vs 植被"上，它把陆地劈成了两半，而不是找出湖。

**真正有效的是光谱双条件**：NDWI 门槛降到 0.02（保住高浊度湖），
同时加 `NIR < 0.20` 挡掉雪缘和裸地。召回从 39.8% 提到 61.8%，
而场景总水体只从 1.16 涨到 1.97 km²——涨幅是 Otsu 的 1/9。

这个结果对方案的意义：

- 浑浊冰湖的漏检不是"阈值没调好"，是**判据维度不够**。
  单靠 NDWI 一个指数，无论阈值取多少都在漏湖和误检之间二选一。
- 加一条 NIR 上限，等于把"低 NDWI 但低 NIR"这个物理特征用上了：
  水在 NIR 强烈吸收，雪/岩/植被不吸收。这才是帕米尔冰湖的判别关键。
- 这条能直接写进创新点：**双指数条件判别替代单指数阈值**，有对比数据支撑。

**遗留问题**：规则 C 仍有 1.66 km² 的场景外水体（雪缘湿痕、薄云阴影）。
下一步应叠加最小面积 + 紧凑度过滤（`extract_lakes` 已有面积过滤，
需补紧凑度），把碎片清掉。这属于精修，不影响主结论。

### 7.9 克亚吉尔面积时序：跑通了，而且抓到了溃决前的满蓄状态

`scripts/kyagar_series.py`，2016–2025，每年在消融期内取**覆盖最完整**的一景
（不是云量最低的，理由见本节末）：

| 年份 | 日期 | 瓦片 | 窗口 km² | 面积 km² |
|---|---|---|---|---|
| 2016 | 06-27 | T43SGV | 7.4 | 0.077 ⚠ |
| **2017** | 07-27 | T43SFV | 37.8 | **1.825** |
| **2018** | **08-06** | T43SFV | 37.8 | **1.825** |
| 2019 | 09-20 | T43SFV | 37.8 | 0.215 |
| 2020 | 08-25 | T43SGV | 7.4 | 0.061 ⚠ |
| 2021 | 07-26 | T43SFV | 37.8 | 0.573 |
| 2022 | — | — | — | 检索失败 |
| 2023 | 09-14 | T43SFV | 37.8 | 0.154 |
| 2024 | 08-14 | T43SFV | 37.8 | 0.130 |
| 2025 | 09-28 | T43SFV | 37.8 | 0.132 |

⚠ 2016 与 2020 只有 T43SGV 的窄条可用（7.4 km² 窗口），面积系统性偏小，不与其他年份并列比较。

#### 两条实质性发现

**1. 满蓄面积存在平台值 1.825 km²。** 2017-07-27 与 2018-08-06 两次独立观测
都落在 1.8248 / 1.8254 km²——差 0.0006 km²。这不是巧合，而是**地形控制**：
冰坝湖蓄到溢流口高度就停止上涨，所以满蓄面积由坝体地形决定，年际重复。

**2. 2018 年 8 月 6 日（溃决前 4 天）湖面正处于满蓄状态。**
数据库记录 2018-08-10 溃决。也就是说**溃决前最后一次清晰观测，湖面在平台值上**。
这是"面积时序能识别溃决前兆"的第一条直接证据——但单点不能当结论，
需要逐年逐旬加密观测才能确认"到达平台值 → 数日内溃决"这条规律是否成立。

这条如果坐实，就是整个项目最硬的技术点：**冰坝湖的溃决前兆可以简化为
"面积是否触及地形平台值"**，比任何加权风险指数都好验证。

#### 必须修正的两个方法问题

**① 采样日期不一致。** 十年里从 6 月 27 日漂到 9 月 28 日。冰坝湖在消融期内
本身就在持续充水—排水，**年际变化里混进了季节相位**。修正方式：固定物候窗口
（如每年 7 月 1–15 日），窗口内取覆盖最完整的景。

**② 选景不能只看云量。** 克亚吉尔正好压在 T43SFV / T43SGV 的边界上。
云量 0.2% 的那景在 T43SGV 上只覆盖一条 **16 像元宽**的窄缝，湖完全在窗口外，
面积算出来是 0.000 km²。改成按"有效像元数"优先选景后，才拿到 452×372 的完整窗口。

**这条对 `glof.cli fetch` 同样适用**：只按云量选景，可能选中一个几乎不覆盖 AOI 的瓦片。
后续应把"有效覆盖"作为选景的第一排序键——这是个会静默给出错误面积的坑。

### 7.10 加密时序：2018 年溃决前的完整充水曲线

`scripts/kyagar_dense.py`，2018-06-01 → 09-15，逐期观测（13 个可用日期）：

| 日期 | 面积 km² | 日期 | 面积 km² |
|---|---|---|---|
| 06-02 | 0.155 | 07-22 | 1.567 |
| 06-07 | 0.195 | **08-06** | **1.825** ← 平台 |
| 06-12 | 0.236 | **08-11** | **0.645** ← 溃决后 |
| 07-02 | 1.031 | 08-21 | 0.770 |
| 07-07 | 0.877 | 08-26 | 0.032 ⚠ |
| 07-12 | 1.248 | 08-31 | 0.470 |
| | | 09-05 | 0.368 |

数据库记录 **2018-08-10 溃决**。曲线给出的过程是：

1. 6 月初湖面 0.155 km²，缓慢上涨；
2. 6 月中到 7 月初进入快速充水（0.236 → 1.031）；
3. 7 月中下旬继续爬升（1.248 → 1.567）；
4. **8 月 6 日到达 1.825 km²，正是 2017 年测到的同一个平台值**；
5. **8 月 11 日（溃决次日）跌到 0.645 km²。**

**这是"面积时序能识别溃决前兆"的第一条完整证据链**：湖面蓄到地形决定的平台值，
随后数日内溃决。而且平台值 1.825 km² 在 2017-07-27 与 2018-08-06 两次独立观测中重合
（差 0.0006 km²），说明这个阈值是地形控制的、可复现的。

#### 2017 年复现

| 日期 | 面积 km² |
|---|---|
| 06-12 | 0.216 |
| 07-22 | 0.461 ⚠ |
| **07-27** | **1.825** ← 同一平台值 |
| 08-16 | 0.074 ⚠ |
| 09-05 | 0.714 |

2017 也到达 1.825 km²，随后降到 0.074 km²。**平台值跨年复现**，
但 2017 可用日期只有 5 个，充水过程采样不足，不能像 2018 那样画出完整曲线。

#### 必须注明的三个限制

1. **⚠ 标记的日期用了 T43SGV 的窄条窗口（7.4 km²）**，与 T43SFV 的 37.8 km² 窗口不可比，
   面积系统性偏小。`valid_frac` 对这一类问题不敏感（窄条内部也是 100% 有效），
   必须同时看 `valid_px`。
2. **2018-07-07 有一个 unexplained 的回落**（1.031 → 0.877 → 1.248）。
   可能是短期排水，也可能是窗口内薄云。需要结合 SCL 云掩膜才能判定。
3. **"到平台值后几天溃决"还不能当规律**。目前只有 2018 一年有足够密度，
   2017 只有 5 个点。要坐实这条，需要对 2015–2019 五个溃决年都做逐期观测。

#### 这条发现对方案的价值

它把"冰湖溃决风险"从**无法验证的加权指数**，变成了**可观测、可复现的状态量**：

> 冰坝湖的风险状态 ≈ 当前面积 / 地形平台面积

这个比值 >0.95 就该预警。它不依赖专家权重，不依赖主观打分，
评委可以拿任何一个年份的影像自己验算。**这是整个项目最值得写进创新点的一条。**

写方案时要写清季节窗口这个前提。

**PySide6 6.12 的三个环境硬规则**（都是冒烟实测踩出来的，以后任何人写 Qt 测试都会撞）：

1. **QtCharts 必须配 QApplication**：QGuiApplication 下 ChartView 一构造即段错误
   （QtCharts 在 C++ 层链接 QtWidgets，与渲染后端无关）。
2. **QSignalSpy.wait() 阻塞 GIL**：PySide6 6.12 下等待期间工作线程饿死、零信号，
   冒烟必须用 processEvents+sleep 轮询，QSignalSpy 只做记录。
3. **PySide6 6.12 不带字体**：offscreen 测试要设 `QT_QPA_FONTDIR=C:\Windows\Fonts`，
   否则中文标签画不出。

另两个 QML 事实：QML 侧变长多边形用 `PathPolyline`（Repeater 不能作为 ShapePath 子元素，
PathPolyline 只认 `Qt.point()` 列表）；地图点选的 prepared 几何必须先反算到像素坐标
（开发中实测修复了一个 WGS84/像素坐标系错配的真 bug）。

**未覆盖**：真机 GPU 交互手感（冒烟全在 offscreen+software）、界面路径的联网
`build_series` 全流程（仅 years=[] 无网冒烟）、PyInstaller 打包。

### 8.7 两处实测修复（2026-10-28）

**1. 启动链路从 5.18 s 降到 2.22 s（ui_spike 的性能 gate 由 FAIL 转 PASS）**

根因不在算法，在句柄。`data/spike` 那景是 **interleave=pixel + LZW** 的 6 波段
GeoTIFF：GDAL 以块为单位解压，读任何一个波段都要把整块（含全部 6 个波段）解开。
`load_scene` 原来给每个波段各开一个 `rasterio.open()`，GDAL 的块缓存挂在
Dataset 上、互不共享，于是同一块被解压 6 次。

实测同进程三种读数方式（6 波段、2686×3056）：

| 读法 | 耗时 |
|---|---|
| 6 个独立句柄，逐波段读（修复前） | 3887 ms |
| 单句柄，逐波段读 | 826 ms |
| 单句柄，一次 `read(indexes=[1..6])` | 834 ms |

修复：`io.load_scene` 按路径复用句柄（`by_path`），关闭也只关去重后的那一份。
修复后读栈 4391–4457 ms → **1506–1659 ms**，启动链路 5138–5184 ms → **2222–2515 ms**
（多次复跑；单次读数会上下浮动约 ±100 ms，用区间而非单值）。

这条对答辩有用：它说明瓶颈在 I/O 组织而不是 numpy，而且是可解释、可复测的。

**2. 风险截图与表格页截图字节完全相同**

冒烟步骤 5 拍 `app_risk.png`、步骤 6 拍 `app.png`，两处都在"湖泊列表"页、
同一状态下，所以两张图一模一样——作为证据只有一张。现改为步骤 5 拍
**面积时序页**（13 期曲线 + 平台线 + 事件年参考线 + 状态栏 HIGH 摘要），与
步骤 6 的列表页互补；冒烟新增一条断言 `风险截图页显示 13 期曲线`。

另修 `LakeTable.qml` 的末列裁剪：列宽常量合计 680，窗口 860 宽时 TableView
右侧留白，等级色块贴边被裁成 "HI"。改为 `_columnWidth()` 按视口宽度等比分摊，
并挂 `onWidthChanged: forceLayout()`（`columnWidthProvider` 是函数，不参与绑定）。

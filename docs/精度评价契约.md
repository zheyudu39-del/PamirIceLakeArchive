## 1. 目标与已核实的事实

用 ICIMOD HMA GLOF 数据库（`data/raw/GLOF database of High Mountain Asia.zip`，
v4.0，765 条事件）作为**弱真值**，评价水体提取的：

| 指标 | 含义 | 真值形态 |
|---|---|---|
| 覆盖率 | 点位有多少落在影像内 | 可精确算 |
| 点位召回 `point_recall` | 覆盖范围内，点位半径 R 内有提取出水体 | 点 + 半径 |
| 边界 IoU `iou` | 提取多边形与真值多边形的交并比 | 需要面真值 |

**已核实的限制（写进报告时必须声明）：**

1. 研究区（73–79°E, 34–39°N）聚类出 **55 个溃决湖点位**。
2. 本地现有影像只覆盖其中 **1/55** —— 所以必须单独补影像窗口。
3. ICIMOD 是**历史溃决事件**库，溃决后湖可能已排空。因此
   `point_recall` 测的是"当前仍存在水体的湖有没有被检出"，
   **不能叫"GLOF 识别准确率"**。报告里用词必须准确。
4. ICIMOD 没有面边界，只有点 + 高程。所以 `iou` 只在有**人工标注样例**
   时才算；没有标注时，评价结果是 `point_recall`，不得用 IoU 的名义报告。
5. 窗口按点取（半宽 0.03°），场景边界效应会吃掉一部分召回——
   统计时必须区分"景外"与"检出失败"。

## 3. 四条硬约束

1. **不设隐藏默认值。** 阈值、半径、像元尺度一律显式参数。
   项目已有的 `MIN_AREA_KM2` 之类常量放在模块顶部并写清来历。
2. **缺数据就是 `None`，不是 0。** 这是本项目 §8.5 已确立的诚实性规则，
   `accuracy.py` 与 `terrain.py` 必须一致遵守。
3. **不伪造真值。** 没有人工标注就只报 `point_recall`，
   在 `notes` 里写明"未做边界精度评价"。
4. **不碰别人的文件。** 各 agent 只写自己那几行"新增/修改文件"。

## 6. 实测结果（2026-10-28）与结论

### 6.1 抓到了什么

55 个溃决湖点位各取 ±0.03° 窗口（Sentinel-2，2022–2025 消融期，云量 <20%）。
每个窗口约 540–680 × 670 px、4–5 MB。覆盖率低于 98% 的（被景边缘裁切）
不得进入评价集——实测 site003 一度只有 44% 覆盖，若不排除，缺失区域会被
误算成漏检。

### 6.2 评价结果（运行中，26 个窗口时）

```
点位召回率：11.1%（半径 0.15 km，3/27 命中）
提出水体的窗口：17 个
其中距点位 > 1 km：13 个（中位 1.37 km，最大 3.08 km）
NDWI 最大值 < 0.05（附近无水）：1 个
```

距离分布呈明显的双峰：`0.0, 0.07, 0.07`（命中）与
`1.13 … 3.08`（一簇 13 个）。中间几乎没有点。

### 6.3 结论：这套弱真值测不了检出率

**低召回率不是算法性能问题，是真值口径问题。** 两个原因：

1. **ICIMOD 的坐标是历史事件点，不是当前湖的几何中心。** 溃决改变湖盆形态，
   十几公里尺度的偏移是常态。13 个点位都落在 1 km 以外的同一簇，说明
   我们的算法确实在这些窗口里找到了水，只是不在点位那个坐标上。
2. **部分湖确实已排空**（NDWI 最大值 < 0.05），它们提出 0 条是事实。

**因此本轮评价只能回答一个问题**：在当前影像里，ICIMOD 历史点位半径 150 m
内有没有水体。它**不能**回答"算法检出率是多少"。

### 6.4 报告里该怎么写

如实写，同时给出成因，不要把它包装成"算法准确率"：

> 以 ICIMOD 历史溃决点作弱真值时，点位召回率为 11.1%（半径 150 m）。
> 未命中的主因是历史事件坐标与当前残湖几何中心不一致（13/17 个已检出的
> 水体距点位超过 1 km，中位 1.37 km），而非提取算法失效。
> 该方法不适于评价检出率；算法的边界精度需以人工标注面真值为准，
> 本轮未做。

## 8. 坝体位置自动估计（2026-11-02）

§7 留的那个口子——"要真正用上这条判据，需要坝体位置，不是湖心"——
已由 `glof/core/dam_position.py` 补上。`cli risk --dam-position`
可以自动估坝体，不必再手填 `--dem-lat/--dem-lon`。

### 8.1 口径

```
坝体 = 湖边界上 DEM 高程最低的点（水往低处流）
下游方位 = 从出口指向湖质心的反方向（外法线）
坡度 = terrain.downstream_slope()，**不另写一套**
```

坡度只来自 `terrain.downstream_slope`，模块里没有第二份坡度实现——
口径全项目只能有一个。`verify_dam_position.py` 有一条断言专门查这件事
（grep 模块源码里不出现 `polyfit`）。

### 8.2 合成 DEM 上确实更好

造一块东高西低的倾斜平面（真实坡 20°），中间挖一个平底坑当湖：

| 量法 | 下游坡度 | 与真值 20° 的偏差 |
|---|---|---|
| 湖心 | 0.56° | **19.4°** |
| 坝体（边界最低点） | 22.74° | **2.7°** |

平底坑上湖心量不到坡向——这正是 §7 里那个 −0.01° 的成因。
换成坝体位置后偏差从 19.4° 降到 2.7°。

### 8.3 但真实 Kyagar 上仍然量不出来（重要）

用 Copernicus GLO-30 真实 DEM、从 DEM 导出的真实湖盆（面积 1.81 km²，
与项目里 Kyagar 平台值 1.825 km² 吻合）实测：

```
坝体位置  77.16080, 35.68280（边界最低点，高程 4739.4 m，下游方位 291°）
湖心      77.17657, 35.67787
下游坡度  -0.06°
```

**为什么还是接近 0**：Kyagar 是**冰坝湖**，坝体是冰川冰，不是岩体或冰碛。
DEM（GLO-30）量的是**冰面高程**，而冰川背后的真实地形坡度不体现在冰面上。
所以在冰坝湖上，无论用湖心还是坝体，DEM 都量不出坝下游的坡。

**结论**：

- 对**冰碛坝湖**，`--dam-position` 是有效改进（坝体是岩/土，DEM 量得到）。
- 对**冰坝湖**，DEM 这条路本身就不适用。应当走 SAR 或冰川流速产品
  判断冰坝稳定性，而不是量坡度。本项目暂未实现 SAR 分支（见 README）。
- 判据仍会因 `MIN_MEASURABLE_SLOPE_DEG = 1.0` 退回 UNKNOWN，
  **不会把 −0.06° 当成有效量测**。这是设计意图，不是遗漏。

### 8.4 一条接线层面的守卫

`--dam-position` 需要 `--lakes`（湖泊 GeoJSON）与 `--dem`。这两者
容易配错：`--lakes` 若是另一景/另一个 bbox 的提取结果，坝体会被估到
别的湖出口，坡度判据整个失去意义，而且**不会报错**。

所以 CLI 加了一条面积量级校验：`--lakes` 里的主湖面积与面积时序的
最大值差一个量级（< 20% 或 > 5 倍）就报错退出。实测拿 spike 景的
0.0757 km² 去配 Kyagar 的 1.8254 km² 时序会被拦下。
